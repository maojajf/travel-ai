# 旅游路线生成 APP 产品需求文档（PRD）

## 1. 文档信息
- 产品名称：旅游路线生成 APP
- 文档类型：标准 PRD
- 文档语言：简体中文
- 产品形态：APP + 小程序双端一致
- 版本阶段：V1.0
- 文档日期：2026-04-23

## 2. 产品概述

### 2.1 产品定位
面向短途旅行、周末游和城市内游玩用户，提供一款可根据出行天数、目的地城市、预算档位、出行人群快速生成合理旅游路线的智能规划工具。产品重点解决“不会规划”“怕踩坑”“时间有限”“路线不合理”的出游痛点，帮助用户在有限时间内获得一套包含景点、美食、游玩项目的完整行程方案。

### 2.2 产品愿景
让用户只需输入少量条件，即可在较短时间内得到一份可直接执行、体验丰富、路线顺畅的城市游玩计划，形成“输入条件 -> 生成路线 -> 查看行程 -> 调整优化 -> 收藏分享 -> 出行反馈”的完整规划闭环。

### 2.3 闭环定义
本产品首版定义为“规划闭环”，不覆盖机票、酒店、门票、餐饮等交易能力，不包含真实导航和旅行社区。闭环目标是让用户在本产品内完成一次完整的旅游规划、调整、保存、分享与反馈过程。

## 3. 项目背景与问题定义

### 3.1 背景
城市短途旅游用户在出行前通常会遇到以下问题：
- 不知道一个城市在有限时间内应该先去哪里、后去哪里。
- 攻略分散在多个平台，景点、美食、游玩项目难以整合。
- 缺少基于天数和真实时间可行性的路线规划。
- 自己做路线时容易出现折返、赶场、体验过载或预算失控。

### 3.2 目标问题
本产品需要解决以下核心问题：
- 帮助用户在输入天数和城市后，快速得到一份完整的可执行路线。
- 生成结果不能只是景点列表，必须包含景点、美食、游玩项目。
- 路线安排需要兼顾体验丰富度、时间可行性、动线合理性和预算适配性。
- 用户可以在结果基础上继续调整、重生成、保存与分享。

## 4. 产品目标

### 4.1 核心目标
- 支持用户输入目的地城市与出行时长，快速生成最佳旅游路线。
- 支持补充预算档位与出行人群，提升路线个性化程度。
- 输出按天拆分的完整旅游方案，覆盖景点、美食与娱乐项目。
- 让路线在有效时间范围内合理可行，减少明显折返和时间冲突。
- 完成从生成到调整、收藏、分享、反馈的完整产品闭环。

### 4.2 首版业务目标
- 建立最小可用旅游规划能力，覆盖中国境内城市旅游场景。
- 聚焦 1 个城市内的 1 至 3 天短途行程规划。
- 优先保障“体验优先”，同时保证路线顺畅与时间合理。

### 4.3 不纳入首版目标
- 不提供机酒票预订能力。
- 不提供实时导航能力。
- 不提供跨城市联游规划能力。
- 不提供用户社区、游记发布、评论互动功能。
- 不提供多语言国际化能力。

## 5. 目标用户

### 5.1 用户画像
- 周末游客：时间有限，希望快速获得城市一日游、两日游安排。
- 情侣用户：关注氛围感、轻松体验、夜游和拍照打卡。
- 亲子家庭：关注安全性、节奏舒适度、互动性和儿童友好项目。
- 朋友结伴：关注体验多样性、美食丰富度、拍照打卡与娱乐性。
- 单人出游：关注省心、顺路、高效和预算控制。

### 5.2 用户共同诉求
- 少输入，快出结果。
- 路线真实可执行，不是堆砌推荐点。
- 同时覆盖“玩什么、吃什么、怎么走”。
- 可以在生成后快速调整而不用从头规划。

## 6. 使用场景
- 用户计划“五一前的周末去广州玩 2 天 1 夜”，希望快速得到一条包含经典景点、美食和夜游活动的合理路线。
- 情侣用户计划“周末去成都 2 天”，希望路线浪漫、节奏舒适、适合拍照和夜间活动。
- 亲子家庭计划“去长沙玩 3 天”，希望减少频繁换场，优先安排适合儿童体验的项目与餐饮。
- 朋友结伴去重庆，希望在中等预算内体验城市地标、美食和夜生活。

## 7. 产品范围

### 7.1 首版支持范围
- 目的地：国内城市
- 天数：1 天、2 天 1 夜、3 天 2 夜等短途时长
- 可选条件：预算档位、出行人群
- 输出内容：按天路线、时间段安排、景点、美食、游玩项目、交通建议、预计耗时、预计费用、出行提示

### 7.2 首版页面范围
- 首页输入页
- 路线结果页
- 单日详情页
- 路线调整页
- 收藏/历史页
- 分享页

## 8. 核心价值主张
- 比手动查攻略更快：用户只需输入少量信息即可得到整套路线。
- 比普通推荐更完整：不是单点推荐，而是可执行的日程级方案。
- 比碎片攻略更合理：系统自动考虑景点聚合、交通时间、餐食时段与夜间活动。
- 比静态路线更灵活：支持替换、重生成、预算切换与路线再优化。

## 9. 核心流程

### 9.1 用户主流程
1. 用户打开 APP 或小程序，进入首页。
2. 输入目的地城市和出行时长。
3. 可选输入预算档位和出行人群。
4. 点击“生成路线”。
5. 系统返回按天拆分的旅游路线结果。
6. 用户查看路线、地图动线、景点详情、美食建议和游玩项目。
7. 用户可一键重生成、替换某个景点、切换预算档位后重新规划。
8. 用户可收藏路线、查看历史路线、分享给同行人。
9. 出行结束后，用户可对路线结果进行反馈，为后续推荐优化提供依据。

### 9.2 产品闭环流程
输入条件 -> 生成路线 -> 查看日程与地图动线 -> 调整/重生成 -> 收藏/分享 -> 出行后反馈

## 10. 最佳路线定义

### 10.1 定义原则
首版中“最佳旅游路线”采用“体验优先”的生成原则，同时必须满足以下约束：
- 在给定出行时间内可执行。
- 动线合理，减少不必要折返。
- 日程节奏自然，不出现过载安排。
- 预算与用户档位相匹配。
- 覆盖景点、美食、游玩项目三类内容。

### 10.2 优先级排序
1. 体验丰富度
2. 路线顺畅度
3. 时间可执行性
4. 交通成本合理性
5. 预算匹配度

## 11. 功能需求

### 11.1 条件输入
#### 11.1.1 功能说明
用户通过首页输入生成旅游路线所需条件。

#### 11.1.2 输入项
- 必填：目的地城市 `city`
- 必填：出行时长 `duration`
- 选填：预算档位 `budget_level`
- 选填：出行人群 `travel_group`

#### 11.1.3 交互要求
- 城市支持搜索选择。
- 出行时长支持常见模板快捷选择，如 `1天`、`2天1夜`、`3天2夜`。
- 预算档位支持低、中、高三档。
- 出行人群支持单人、情侣、亲子、朋友四类。
- 用户未填写预算或人群时，系统使用默认推荐策略生成路线。

#### 11.1.4 默认规则
- 若未输入具体到达和离开时间，系统按标准游玩时段生成。
- `2天1夜` 默认按 `D1 上午至晚间 + D2 上午至傍晚` 规划。

### 11.2 智能路线生成
#### 11.2.1 功能说明
系统根据输入条件自动生成完整旅游路线。

#### 11.2.2 生成结果必须包含
- 每日主题或概览
- 时间段安排
- 景点推荐
- 美食推荐
- 游玩项目或娱乐活动推荐
- 景点间交通方式
- 景点间预计通勤时间
- 建议停留时长
- 当日预计费用
- 贴士说明

#### 11.2.3 输出结构
系统返回结构化行程数据，支持页面展示和后续编辑。

### 11.3 行程详情展示
#### 11.3.1 功能说明
用户可查看按天、按时间段拆分的完整行程详情。

#### 11.3.2 页面展示要点
- 日程分天展示
- 每个时间段展示对应的景点、美食或活动
- 展示上下一个点之间的通行方式和所需时长
- 展示每个点的建议停留时间
- 展示该天总预算摘要
- 展示提示信息，如避开高峰、建议预约、适合拍照时间等

### 11.4 路线调优
#### 11.4.1 功能说明
用户在生成结果后可进行轻量调整。

#### 11.4.2 首版支持能力
- 一键重生成整条路线
- 替换单个景点或活动
- 切换预算档位后重新生成
- 切换出行人群后重新生成

#### 11.4.3 首版暂不支持
- 自由拖拽调整全日程
- 用户自定义新增复杂途经点
- 多城市混排行程

### 11.5 收藏与分享
#### 11.5.1 收藏
- 用户可收藏当前路线方案。
- 收藏后可在历史页再次查看。

#### 11.5.2 历史记录
- 记录用户生成过的路线结果。
- 支持再次打开并继续调整。

#### 11.5.3 分享
- 支持生成可分享的路线摘要页。
- 分享内容需至少包含城市、天数、路线亮点和每日概要。

### 11.6 反馈与再推荐
#### 11.6.1 功能说明
用户出行后可对路线结果进行反馈，帮助后续推荐优化。

#### 11.6.2 首版反馈类型
- 行程是否合理
- 景点是否值得
- 美食推荐是否满意
- 节奏是否过快或过慢

## 12. 路线生成规则

### 12.1 总体规则
- 同一区域优先聚合，避免跨区频繁往返。
- 必须生成可落地的日程路线，而非简单推荐列表。
- 每日行程必须同时覆盖景点、美食、游玩项目。
- 路线需符合正常出游时间分布，不安排极端赶场。

### 12.2 时间规则
- 每个景点和活动必须带有建议停留时长。
- 相邻点位之间必须估算通勤时间。
- 餐饮安排需插入中午和晚间合理时段。
- 夜游活动只允许安排在晚间。
- 单日不允许出现明显超载，例如连续高强度景点安排且缺少休息或餐饮时间。

### 12.3 动线规则
- 优先选择空间上相对聚集的景点组合。
- 优先从上午开始安排适合白天游玩的内容，傍晚和夜间安排夜景、夜市、演出、酒吧或休闲活动。
- 尽量减少“来回穿城”的路线。

### 12.4 个性化规则
- 亲子：优先轻松、互动、安全、停留时间可控的场景。
- 情侣：优先氛围感、夜游、观景、拍照、仪式感餐饮。
- 朋友：优先体验多样性、打卡、美食覆盖和社交娱乐项目。
- 单人：优先效率、便利、省心和预算可控。

### 12.5 预算规则
- 低预算：优先免费或低门票景点、平价餐饮、公共交通。
- 中预算：兼顾品质与性价比，适度加入特色体验项目。
- 高预算：增加品质餐饮、特色项目、高舒适度交通建议。

## 14. 数据接口定义

### 14.1 输入数据结构
```ts
type GenerateRouteInput = {
  city: string;
  duration: string;
  budget_level?: "low" | "medium" | "high";
  travel_group?: "solo" | "couple" | "family" | "friends";
};
```

### 14.2 输出数据结构
```ts
type ItineraryItem = {
  time_slot: string;
  poi: string;
  food_recommendation: string;
  activity: string;
  transport_mode: string;
  travel_time: string;
  stay_duration: string;
  estimated_cost: string;
  tips: string;
};

type DayPlan = {
  day_index: number;
  day_title: string;
  day_budget_summary: string;
  itinerary: ItineraryItem[];
};

type GenerateRouteOutput = {
  city: string;
  duration: string;
  budget_level: "low" | "medium" | "high";
  travel_group: "solo" | "couple" | "family" | "friends";
  itinerary: DayPlan[];
};
```

### 14.3 字段说明
- `city`：目标出游城市
- `duration`：出行时长描述
- `budget_level`：预算档位
- `travel_group`：出行人群类型
- `day_index`：第几天
- `time_slot`：时间段
- `poi`：景点或核心目的地
- `food_recommendation`：推荐餐饮
- `activity`：推荐活动或游玩项目
- `transport_mode`：建议交通方式
- `travel_time`：预计通勤时间
- `stay_duration`：建议停留时长
- `estimated_cost`：预计费用
- `tips`：附加提示

## 15. 业务规则与异常处理

### 15.1 业务规则
- 城市与天数为生成路线的前置条件，缺一不可。
- 预算和人群未填写时，按平台默认推荐策略生成。
- 输出结果必须按天拆分，且至少包含一个完整白天行程。
- 系统生成结果需保证内容完整，不允许返回空的日程节点。

### 15.2 异常场景
- 若目标城市数据不足，提示用户当前城市路线能力建设中，并推荐热门路线模板。
- 若用户输入过长天数，首版提示仅支持短途行程规划。
- 若用户切换条件后无法生成差异化方案，系统应提示当前条件下推荐结果相近。

## 16. 非功能需求

### 16.1 性能要求
- 首版生成结果应在 10 秒内返回首版结果。
- 页面切换和查看详情应保持流畅。

### 16.2 终端一致性
- APP 与小程序在信息结构、核心功能、交互主路径上保持一致。
- 展示以移动端优先设计。

### 16.3 稳定性要求
- 支持城市、天数、预算、人群组合下的稳定生成。
- 对常见热门城市的生成能力优先保障。

## 17. 示例输出口径

### 17.1 示例输入
- 城市：广州
- 时长：2天1夜
- 预算：中预算
- 人群：朋友

### 17.2 示例输出要求
- D1 和 D2 都有完整行程安排。
- 每天都包含景点、美食、游玩项目。
- 动线应尽量围绕相近片区展开，不出现无意义折返。
- D1 可安排城市地标、特色餐饮和夜游内容。
- D2 可安排文化体验、轻松收尾和返程前可执行行程。

## 18. 验收标准

### 18.1 功能验收
- 用户输入城市和天数后可以成功生成路线。
- 用户可补充预算和人群并得到相应差异化路线。
- 用户可查看分天路线、单日详情、交通建议和预算摘要。
- 用户可执行重生成、替换、收藏、分享等核心动作。

### 18.2 结果验收
- `广州 + 2天1夜 + 中预算 + 朋友出游` 能生成完整双日路线。
- 每天结果都覆盖景点、美食、游玩项目。
- 路线中的点位顺序合理，通勤时间累计可解释。
- 不出现明显反复折返。
- 单日行程时长不过载。
- 餐饮时段自然分布，夜间活动不出现在白天。

### 18.3 个性化验收
- 亲子模式下推荐更偏轻松和互动项目。
- 情侣模式下推荐更偏氛围感和夜游。
- 朋友模式下推荐更偏体验和打卡。
- 不同预算档位下，餐饮、门票、活动等级和日均花费有明显差异。

### 18.4 闭环验收
- 用户可收藏当前路线。
- 用户可查看历史路线。
- 用户可分享路线摘要给同行人。
- 用户可在出行后进行路线反馈。

## 20. 版本边界与后续演进

### 20.1 V1.0 边界
- 聚焦城市内短途路线规划。
- 完成输入、生成、查看、调整、收藏、分享、反馈的基础闭环。

### 20.2 后续可扩展方向
- 增加到达时间、离开时间、节奏偏好等更细输入项。
- 增加酒店、门票、餐饮预订的交易能力。
- 增加地图导航联动和实时营业状态。
- 增加用户评价、攻略内容沉淀和社区分享。
- 增加跨城市联游规划能力。
